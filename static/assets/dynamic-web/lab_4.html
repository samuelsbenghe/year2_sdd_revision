1. Connecting the Dots: Why Are We Moving to the Browser?

If you have found the first three weeks challenging, take a breath—this section explains how the pieces fit together.

Over the past three weeks, we have worked almost entirely inside the command-line terminal:

  1. Week 1 (Servers & SSH): You used ssh to open an encrypted connection to your virtual server on igor and edited files directly on that remote machine using nano.
  2. Week 2 (APIs & HTTP): You built backend routes and tested them using curl. You saw that every web interaction consists of an HTTP Request (a method like GET or POST, a URL path, and headers) and an HTTP Response (a numeric status code like 200 OK or 404 Not Found, response headers, and a text body).
  3. Week 3 (Databases): You learned how to store persistent data inside relational SQL tables so your server doesn’t forget everything when it restarts.
  4. Week 4 (Network Protocols): We traced how those messages physically travel from your server to a user’s machine—moving from electrical voltages on copper wires, through local switches (MAC addresses) and global routers (IP addresses), inside numbered TCP segments, up to the Application layer (HTTP).

The Big Question: Where does the Web Browser fit in?

When a real person visits your web application, they do not open a terminal and type curl. They use a web browser (Chrome, Firefox, Safari, Edge).

A web browser is an HTTP client with a graphical rendering engine. When you type a URL into the address bar:

  1. The browser sends an HTTP GET request across the network (just like curl).
  2. The server sends back an HTTP response containing raw text (HTML, CSS, JavaScript, or JSON).
  3. Crucial Step: Instead of dumping raw HTML text onto the screen like curl does, the browser parses that text and builds an interactive, visual tree of objects in your computer’s memory called the DOM (Document Object Model).

Today, you will learn how to use Browser Developer Tools (DevTools)—the built-in inspection suite that lets you see, edit, debug, and manipulate the DOM, CSS layouts, JavaScript state, and live network packets.

Important Reassurance for Beginners: Everything you edit, delete, or break inside Browser DevTools only affects the temporary copy of the webpage sitting in your own laptop’s RAM. You cannot accidentally delete files on igor or break a live website for other people by editing things in the Elements or Console tabs. If you break the page layout completely, press F5 (or Ctrl + R / Cmd + R) to reload the page from the server and start fresh!

3. Task 1: The Elements Tab, the CSS Box Model & document.designMode

Conceptual Background: Source Code vs. The DOM

If you right-click a webpage and choose View Page Source (Ctrl + U), you see the raw HTML text file exactly as it was written on the server—identical to what curl prints.

However, the Elements tab (called Inspector in Firefox) shows you the live DOM tree. If JavaScript adds a new paragraph, deletes a button, or changes a colour, the Elements tab updates in real time.

Step 1.1: Uncovering “Hidden” Elements in the DOM

  1. Look at your rendered devtools-lab.html page in the browser. You see the header, two cards, and the form at the bottom.
  2. Now look inside the Elements tab in DevTools. Expand the <body> tag by clicking the small arrow next to it.
  3. Find <div class="secret-panel" id="admin-debug"> in the DOM tree and click on it.
  4. Look at the Styles pane on the right side of the Elements tab. You will see:
.secret-panel {
  display: none;
  ...
}
  1. Hover your mouse over the display: none; rule in the Styles pane and uncheck the checkbox next to it.
  2. What just happened? The orange Admin Debug panel immediately appeared on the page!
    • Why this matters: Beginning developers sometimes try to “hide” admin buttons or restricted information using CSS (display: none or visibility: hidden). As you just proved, the data was already sent over the network in the HTTP response and sits right there in the DOM.

Step 1.2: Live CSS Debugging & The Box Model

Suppose you want to change the spacing or colours of the .card elements without constantly editing your file and refreshing.

  1. Click the Select an element icon at the top-left of the DevTools bar (an icon showing a mouse cursor inside a dashed square, or press Ctrl + Shift + C).
  2. Move your mouse over the “Database Node Alpha” card on the webpage. Notice how DevTools draws shaded colour overlays over the element:
    • Blue overlay: The inner content area (width × height).
    • Green overlay: The padding (space inside the border).
    • Orange overlay: The margin (space outside the border pushing other elements away).
  3. Click the card to lock your selection onto <div class="card">.
  4. In the Styles pane on the right, find the .card selector rule:
    • Click on the colour swatch square next to border: 1px solid #374151; and drag the colour picker to bright cyan (#38bdf8). Notice how both cards on the page update simultaneously because they share the .card class!
    • Click at the end of the .card rule block to add a new property. Type padding: 3rem; and press Enter.
    • Double-click the 3rem value and press your Up and Down Arrow keys on your keyboard—watch the card padding grow and shrink smoothly by 1 unit per keypress!

Step 1.3: The One-Liner Layout Stress-Tester (document.designMode)

When you build a frontend interface that displays data from a database (Week 3), you rarely know how long the text will be. What if a user enters a 90-character name, or an article title is three times longer than your sample text?

Instead of editing HTML tags one by one in the Elements tree, you can turn the entire webpage into a live word processor using a single line of JavaScript.

  1. Click on the Console tab at the top of DevTools.
  2. Type the following command at the > prompt and press Enter:
document.designMode = "on";

(Note: You can also achieve a similar effect on individual elements by adding the contenteditable="true" attribute in HTML, or setting document.body.contentEditable = "true" in the Console).

  1. Now click directly on the words "System Status Dashboard" on the webpage itself and start typing!
  2. Try the following layout stress-tests right on the page:
    • Test 1 (Flexbox collision): Click on "System Status Dashboard" and type two full sentences of text. Watch how the heading wraps onto multiple lines and pushes against the "Server Online" badge on the right. Because .header-bar has white-space: nowrap on .badge, the badge stays intact—what happens if you click inside the "Server Online" badge and type 50 characters there? It overflows right off the edge of the box!
    • Test 2 (Uneven Grid Cards): Click inside the paragraph of “Database Node Alpha” and paste 5 lines of text, then delete all the text inside “API Gateway Beta”. Observe how CSS Grid (display: grid) automatically stretches the height of the right-hand card so both cards in the row stay equal height!
  3. When you are finished testing the layout, turn design mode back off in the Console:
document.designMode = "off";

MDN Reference Guides for Task 1: * Search MDN for Document.designMode and HTMLElement.contentEditable to read how browsers implement live editing. * Search MDN for Introduction to the CSS basic box model if you are ever unsure whether to use padding or margin.

4. Task 2: The Console & Manipulating the DOM with JavaScript

Conceptual Background: Why Use the Console?

In Week 1, your SSH terminal let you type commands to inspect and control your remote Linux server. The Console tab is an interactive JavaScript environment (REPL — Read-Eval-Print Loop) that lets you inspect and control the webpage currently loaded in your browser.

It serves two primary purposes: 1. Diagnostic Output: Any syntax errors, failed network requests, or console.log() messages from your scripts appear here. 2. Live DOM Scripting: You can write and test JavaScript code against the live page before putting that code into your .js files.

Step 2.1: Selecting and Modifying Elements (querySelector)

The global document object represents the entire webpage. To grab a specific HTML element so JavaScript can change it, we use document.querySelector() (which takes any valid CSS selector, like #id, .class, or tag).

Run each block below in your Console tab one at a time and watch your sandbox page change:

  1. Grab an element by its ID and change its text and colour:
// 1. Select the badge element using its CSS ID selector (#status-badge)
const badge = document.querySelector("#status-badge");

// 2. Print the element to verify we grabbed the right node
console.log("Selected element:", badge);

// 3. Mutate its text content and inline CSS style
badge.textContent = "Database Overload!";
badge.style.backgroundColor = "#dc2626";
  1. Grab multiple elements at once (querySelectorAll): What if you want to update all elements that share a class? document.querySelectorAll() returns a NodeList (similar to an array) containing every matching element on the page.
// Select every <strong class="conn-count"> element inside the cards
const counters = document.querySelectorAll(".conn-count");

// Loop through each element and multiply its current number by 10
counters.forEach((el) => {
  const currentVal = parseInt(el.textContent, 10);
  el.textContent = currentVal * 10;
  el.style.color = "#fbbf24";
});

Step 2.2: Generating New DOM Elements from Data Arrays

In Week 3, you learned that a database query returns rows of structured data (which your Week 2 API sends over HTTP as a JSON array of objects). How does a frontend webpage turn an array of JavaScript objects into visible HTML cards?

Copy and paste this snippet into the Console to dynamically create and append two brand-new server cards to #user-cards:

// Simulate an array of records returned from a database API
const newServers = [
  { name: "Cache Node Gamma", desc: "In-memory Redis cluster for fast session lookup.", connections: 412 },
  { name: "Backup Vault Delta", desc: "Nightly encrypted SQL snapshot storage.", connections: 2 }
];

const grid = document.querySelector("#user-cards");

newServers.forEach((srv) => {
  // Create a new <div class="card"> element in memory
  const card = document.createElement("div");
  card.className = "card";

  // Populate its inner HTML using a template literal
  card.innerHTML = `
    <h3>${srv.name}</h3>
    <p class="description">${srv.desc}</p>
    <p>Active Connections: <strong class="conn-count">${srv.connections}</strong></p>
  `;

  // Attach the newly created card to the live DOM grid
  grid.appendChild(card);
});

Now switch back to the Elements tab and expand <div class="card-grid" id="user-cards">. You will see four <div class="card"> elements in the live DOM tree—even though your original HTML file only had two!

Step 2.3: Essential Console Power Shortcuts

DevTools includes special shorthand variables that only work inside the Console:

  • $0 (The Currently Inspected Element):
    1. Go to the Elements tab and click on any element (for example, <h1 id="main-title">).
    2. Switch to the Console tab, type $0 and press Enter. It immediately returns that <h1> node!
    3. Now type $0.style.transform = "rotate(-2deg)" and press Enter.
  • console.table() (Structured Data Viewer): Instead of expanding nested arrows in console.log(), pass any array of objects to console.table(). Run this in the Console to see a formatted spreadsheet of every card currently on your page:
const summary = Array.from(document.querySelectorAll(".card")).map((card, idx) => ({
  cardIndex: idx,
  heading: card.querySelector("h3")?.textContent || "No Heading",
  textLength: card.textContent.trim().length
}));

console.table(summary);

5. Task 3: The Network Tab — Connecting TCP/IP, HTTP & fetch()

Conceptual Background: Seeing the Lecture Stack in Real Life

In the lecture, we built the 5-layer Internet model: * Layer 5 (Application): HTTP requests, methods (GET, POST), status codes (200, 404), headers, and JSON/HTML bodies. * Layer 4 (Transport): TCP ports (80, 443), the 3-Way Handshake (SYN, SYN-ACK, ACK), and segment reassembly. * Layer 3 (Network): IP addresses (172.x.x.x) and DNS resolution.

The Network tab records every single network transaction your browser performs and lets you inspect Layers 3, 4, and 5 for every request.

Step 3.1: Configuring the Network Tab Properly

  1. Click the Network tab in DevTools.
  2. Check the “Disable cache” box near the top toolbar.
    • Why? Browsers save copies of files on your hard drive so repeat visits load faster. If you leave cache enabled, the browser might not actually send packets over the network, or the server will reply with 304 Not Modified (an empty body) instead of 200 OK. When debugging, always check Disable cache.
  3. Turn on the Layer 3/4 “Remote Address” column:
    • Right-click on the grey table header bar (Name | Status | Type | Initiator | Size | Time).
    • From the popup menu, check Remote Address and Protocol.
    • You will now see the exact destination IP Address and TCP Port (e.g., :443 for HTTPS) for every single request!

Step 3.2: Wiring Up Our Sandbox Button to Make Live HTTP Requests

Right now, clicking the “Load User via HTTP” button on your devtools-lab.html page doesn’t do anything because we haven’t attached an event listener to it yet. Let’s wire it up using the browser’s fetch() API so we can watch the network traffic live!

(Note: Why is the URL below written using ['https:', '', 'jsonplaceholder.typicode.com', 'users'].join('/')? Because it constructs the exact URL string cleanly in JavaScript without text-editors or markdown viewers turning it into a clickable hyperlink when you copy and paste!)

  1. Open the Console tab, copy and paste this entire block, and press Enter:
const fetchBtn = document.querySelector("#fetch-btn");
const userIdInput = document.querySelector("#user-id");
const outputBox = document.querySelector("#api-output");

fetchBtn.addEventListener("click", async () => {
  const id = userIdInput.value;
  // Construct the API URL cleanly: [https://jsonplaceholder.typicode.com/users/](https://jsonplaceholder.typicode.com/users/){id}
  const apiUrl = ["https:", "", "jsonplaceholder.typicode.com", "users", id].join("/");

  outputBox.textContent = `Sending HTTP GET request to ${apiUrl} ...`;

  try {
    const response = await fetch(apiUrl);

    console.log("HTTP Status Code:", response.status);
    console.log("Content-Type Header:", response.headers.get("content-type"));

    if (!response.ok) {
      outputBox.textContent = `Server returned error status: ${response.status}`;
      return;
    }

    const userData = await response.json();
    console.table(userData);
    outputBox.textContent = JSON.stringify(userData, null, 2);
  } catch (err) {
    outputBox.textContent = `Network Error: ${err.message}`;
  }
});

console.log("Button listener attached! Click 'Load User via HTTP' on the page.");
  1. Keep the Network tab open (and click the Fetch/XHR filter pill near the top so you only see JavaScript API calls).
  2. Now click the green “Load User via HTTP” button on your webpage!

Step 3.3: Dissecting the Request in the Network Tab

A new row named 1 (the user ID you requested) just appeared in the Network table. Click on that row 1 to open the detailed inspector panel on the right:

  1. Headers Sub-Tab (Application Layer):
    • General: Look at Request URL, Request Method: GET, Status Code: 200 OK, and Remote Address (the IP address and :443 port of the remote server).
    • Response Headers: Find content-type: application/json; charset=utf-8. Remember the lecture slide on ASCII/UTF-8? That header tells the browser how to decode the incoming binary stream of 1s and 0s into characters!
    • Request Headers: Look at User-Agent and Accept.
  2. Preview & Response Sub-Tabs:
    • Response shows the raw text string sent inside the TCP packets.
    • Preview parses that JSON string into an interactive collapsible tree.
  3. Timing Sub-Tab (Transport & Network Layers): Click on Timing and look at the horizontal bars:
    • DNS Lookup: How many milliseconds it took to look up the IP address for the domain name (Layer 3).
    • Initial connection: How many milliseconds the TCP 3-Way Handshake (SYN → SYN-ACK → ACK) took before a single byte of HTTP could be sent (Layer 4)!
    • Waiting for server response (TTFB — Time to First Byte): How long the request spent traveling across ISP routers to the server, querying the backend data, and sending the first packet back.
    • Content Download: Receiving the TCP data segments.

Step 3.4: Exporting Browser Traffic to curl

Want to see how the browser’s fetch() call relates to your Week 2 terminal commands?

  1. In the Network tab, right-click on the 1 request row.
  2. Select Copy → Copy as cURL (bash).
  3. Open your terminal (or paste it into a text editor). You will see a complete curl command with -H flags for every single HTTP header your browser sent!

6. Level 6 Extension Activities: Grow Your Practice & Connect the Dots

If you are in Year 3 (Level 6)—or you have completed Tasks 1–3 and want to master the techniques used by professional full-stack and security engineers—complete the three architectural challenges below.

Extension A: Bypassing Client-Side Form Validation (Security Architecture)

Look at the HTML <input> inside devtools-lab.html:

<input type="number" id="user-id" name="userId" min="1" max="10" value="1" required>

The public test API only has 10 users (IDs 1 through 10). What if a developer relies on min="1" max="10" or front-end JavaScript checks to protect their backend SQL database from invalid IDs, negative numbers, or SQL injection strings?

  1. Method 1 (DOM Mutation): Right-click the input box on the page → Inspect. In the Elements tab, double-click type="number" and change it to type="text", and delete min="1" max="10". Now type 9999 (or 1/posts) into the input box on the page and click Load User via HTTP.
    • Look at the Network tab: when you request User 9999, what HTTP Status Code does the server return? (404 Not Found!).
    • What happens when you type 1/todos into the box and click the button? You just traversed to a completely different API route (/users/1/todos) because the client-side code concatenated user input directly into the URL path!
  2. Method 2 (Direct Network Replay): Right-click any request in the Network tab → Copy → Copy as fetch. Paste it into the Console and modify the URL, method, or headers directly in JavaScript—completely bypassing the HTML page and all of its event listeners.
  3. Architectural Takeaway: Client-side validation (HTML attributes, CSS hiding, browser JavaScript) exists purely for User Experience (UX) to give honest users quick feedback. Your server-side API code on igor (Week 2) and your database constraints/prepared statements (Week 3) are the only true security boundary.

Extension B: Simulating Congested Network Physics & Fixing Race Conditions

In the lecture, we saw how congested routers and packet loss delay TCP delivery. On your local machine or fast campus Ethernet, an API call finishes in 20ms. What happens when a user is on a train with 600ms latency?

  1. In the Network tab toolbar, find the Throttling dropdown (it defaults to No throttling, right next to Disable cache).
  2. Switch it to Slow 3G.
  3. Now type 2 into the User ID box and click Load User via HTTP, then immediately type 3 and click Load User via HTTP again while the first request is still pending!
  4. Watch the Network waterfall: both requests are in flight at the same time.
  5. Engineering Challenge: Modify the button event listener in your Console (or in devtools-lab.html) so that:
    • While a fetch() request is in flight, fetchBtn.disabled = true and fetchBtn.textContent = "Loading..." so a user on a slow connection cannot accidentally trigger 10 duplicate database requests by mashing the button.
    • Inside a finally { ... } block, re-enable the button and restore its original label once the response (or error) finishes.

Extension C: Building a Live Network Telemetry Interceptor (window.fetch Monkey-Patching)

How do monitoring tools (like Sentry, Datadog, or browser privacy extensions) log and measure every API call a webpage makes without editing the application’s source code? They wrap the browser’s native window.fetch function!

Paste this interceptor into your Console, and then click your “Load User via HTTP” button (try it both with No throttling and with Slow 3G, and try requesting User 999 to trigger a 404):

// 1. Keep a reference to the browser's genuine fetch implementation
if (!window._nativeFetch) {
  window._nativeFetch = window.fetch;
}

// 2. Replace window.fetch with an instrumentation wrapper
window.fetch = async function (...args) {
  const startTime = performance.now();
  const targetUrl = args[0];

  console.info(`[Telemetry] Outgoing HTTP Request -> ${targetUrl}`);

  try {
    const response = await window._nativeFetch.apply(this, args);
    const elapsedMs = (performance.now() - startTime).toFixed(1);

    // Log a warning if the server returned an error status (4xx/5xx) or took > 500ms
    if (!response.ok || elapsedMs > 500) {
      console.warn(
        `[Telemetry ALERT] Slow or Failed Request! Status: ${response.status} | Time: ${elapsedMs}ms \vert{} URL:${targetUrl}`
      );
    } else {
      console.info(
        `[Telemetry OK] Status: ${response.status} \vert{} Time:${elapsedMs}ms`
      );
    }

    return response;
  } catch (networkErr) {
    console.error(`[Telemetry CRITICAL] TCP/Network Failure for ${targetUrl}:`, networkErr);
    throw networkErr;
  }
};
  • Level 6 Stretch Task: Extend the if (!response.ok || elapsedMs > 500) block above so that whenever a slow or failed HTTP request is detected, your script dynamically creates a red notification toast banner (document.createElement("div")) at the top of document.body displaying the HTTP status code and response time in milliseconds!
